### 1.3 架构真相：MCP 与 CLI 不是平行双通道（颠覆性结论）

上游 README 官方原文：

> "All active CBM processes must run the exact same version, executable build, coordination ABI, and canonical cache root. MCP servers, hooks, one-shot CLI commands, temporary index workers, and the daemon share a crash-safe **OS admission barrier**."

本机实测错误演化（硬证据）：

```
未设 CBM_CACHE_DIR     → secure CLI coordination could not be created (cache-private)
设为 <部署态>\data\cache → active account daemon uses a different cache directory
                          (active d91b00c9…; requested f8093689…)
```

**由此确立三条约束：**

1. **CLI 不是 MCP 的兜底通道**。二者共享准入屏障，缓存根不一致时 CLI 启动即失败。脚本中"MCP 失败 → 降级 CLI"的设计前提不成立。
2. **CLI 必须显式导出 `CBM_CACHE_DIR`**。由日志路径 `${CBM_CACHE_DIR}/logs/cbm-daemon.log` 反推，守护进程缓存根 = `D:\codebase-memory-mcp\data`。开发态脚本第 102 行已设 `CbmCacheDir = (Join-Path $PSScriptRoot "data")`，取值正确，需保留。
3. **Agent 无法启动本地 exe（环境约束，本轮实测确立）**

   本轮在守护进程**已完全停止**（无 `codebase-memory` 进程、9749 与 8082 端口均无监听）的状态下复测，结果：

   | 通道 | 读取 exe | 执行 exe |
   |---|---|---|
   | Bash | 成功（`head -c 16` 返回 PE 文件头 `MZ`） | 失败，退出码 `126` Permission denied |
   | PowerShell | 失败（`OpenRead` 拒绝访问） | 失败（安全策略拦截 `[Process]::Start`） |

   同一环境下部署态目录**可写**（可创建并删除临时文件），故不是文件系统权限问题。

   **结论**：此前"daemon 以独占方式持有 exe 映像"的推测**已被证伪**。真实原因是 **Agent 的 Bash 与 PowerShell 工具均无法启动本地 exe 进程**，属工具侧安全策略约束，与守护进程是否运行无关。

   **影响**：阶段 1 的"替换 exe 文件"可行（目录写权限具备）；但"执行 exe 验证版本"与阶段 3 的 CLI 侧用例（T3/T4）**必须由用户手动执行**。

4. **停用守护进程仍是阶段 1 的必要前置**：目的不是解除访问限制，而是避免替换文件时目标文件被进程占用。此动作用户已于本轮完成。

## 2. 目标与非目标

### 2.1 目标

1. 引擎由 v0.10.2 升级至 v0.10.8，消除聚合少计与私有锁相关的已知缺陷。
2. 开发态脚本回流部署态成果，并适配 v0.10.8 的参数与返回结构变化。
