# 通用调用方法（Invocation Reference）

本文档是 `mimo.code` 的调用手册，**环境无关**：不绑定任何具体连接器命名、分组名或本机路径。读完即可在任意接入了 `mimo.code` 的 Agent 上正确发起调用。

## 1. 工具定位：mimo 提供什么

接入 `mimo.code` 的 Agent 通常还能看到同族的 `mimo.chat`（纯问答对话）与 `mimo.health`（健康检查）。三者共用同一 MiMo 额度：

| 工具 | 本质 | 用途 | 何时用 |
|---|---|---|---|
| `mimo.chat` | 直接调用 MiMo 大模型 API 对话（OpenAI 兼容格式） | 纯问答、解释、聊天 | 只需要一段文字回答，不涉及"改文件/跑任务" |
| `mimo.code` | 基于 `mimo run` 非交互模式执行完整编程/文本任务 | 编写/修改/调试/审查代码、项目分析、方案讨论、内容生成 | 需要产出代码/文件、改动目录、或对项目做工程性分析/讨论 |
| `mimo.health` | 健康检查 | 确认底层模型、API 端点、密钥、超时等配置 | 首次使用或怀疑连接异常时 |

> 本技能聚焦 `mimo.code`。纯聊天用 `mimo.chat`（二者共用额度）。

## 2. 接入形态（先探测，再调用）

`mimo.code` 在不同 Agent 上的暴露方式不同，**不要写死工具名**。首次使用先做接入探测，确认实际形态。`mimo.code` 只存在以下两种接入形态，本技能对两者通用：

**形态 A — `mimo.code` 通过 `Dynamic-mcp` 工具中转连接到 Agent**
经由动态工具通道（动态 MCP 代理）调用，由 Agent 侧的"调用动态工具"入口（如 `call_dynamic_tool`）转发：
```
Tool: <你的动态工具调用入口>            # 例如 mcp__Dynamic-mcp__call_dynamic_tool
args: { group: <你的 mimo 分组名>, name: "mimo.code", args: { ... } }
```
- 探测：`list_groups`（或等价接口）确认 mimo 分组已连接；`get_dynamic_tools`（mode=full）取 `mimo.code` 精确 schema。
- 分组名（如 `mimo-mcp`）因环境而异，**以探测到的为准**。

**形态 B — `mimo.code` 以 MCP 服务方式直接连接 Agent**
`mimo.code` 作为原生 MCP 工具直接暴露（工具名可能为 `mimo__code` 或 `<前缀>__code`，前缀取决于该 MCP 服务的注册名）：
```
Tool: <探测到的 mimo.code 工具名>        # 例如 mimo__code
args: { prompt: "...", working_dir: "...", format: "text", skip_permissions: true }
```
- 探测：查阅当前 Agent 的 MCP 工具列表，确认 `mimo.code` 的确切工具名与参数。

> 两种形态的参数语义完全一致（见第 3 节），区别仅在"如何寻址到 mimo.code"这一层：形态 A 多一层 `group`/`name` 路由包装，形态 B 直接是原生 MCP 工具。本技能其余内容（参数、边界、协同范式、防死锁）对两种形态通用。若一个 Agent 同时以两种形态暴露，择一使用即可，无需重复调用。

## 3. `args` 参数全表（与接入形态无关）

| 参数 | 类型 | 必填 | 说明与经验 |
|---|---|---|---|
| `prompt` | string | 是 | 任务自然语言描述。**工程任务必须显式约束作用域**：编写→"只写 X 文件"；修改→"只修改 Y 文件，保持签名不变"；讨论/分析→"只分析、不写任何文件"。约束越清晰，误写风险越低。 |
| `working_dir` | string | 否 | 绝对路径，所有文件读写根目录。**默认直接用真实仓库的工作副本目录（不用沙箱）**；仅在受硬约束（mimo 部署形态强制 `<SANDBOX>`、主Agent 安全策略禁止直写真实仓库、或高风险/边界探索性测试需主动隔离）时，才回退为隔离沙箱 `<SANDBOX>`。详见下方「`working_dir` 策略与真实仓库衔接」。 |
| `format` | string | 否 | `"text"` 返回人类可读文本；`"json"` 返回结构化。编程/讨论任务用 `"text"` 即可。 |
| `continue_session` | bool | 否 | 跨调用延续上下文开关。**是否生效因环境而异**（见第 4 节）。多轮记忆的最稳妥兜底是由主Agent 在 `prompt` 中回灌历史。 |
| `skip_permissions` | bool | 否 | 设为 `true` 跳过文件操作权限确认，使非交互执行不挂起。**建议始终设为 `true`**。 |

### 3.1 `working_dir` 策略与真实仓库衔接

本技能**默认主张用真实仓库、不用隔离沙箱**——能直接让 mimo 在真实工作副本里产出，主Agent 直接对真实仓库提交，省去搬运环节。仅在以下**硬约束**出现时才回退隔离沙箱 `<SANDBOX>`：

- mimo 的部署形态本身强制使用 `<SANDBOX>`（无法改写其工作根）；
- 主Agent 的安全/合规策略禁止 mimo 直接写真实仓库；
- 高风险或探索性测试（超长 prompt、大项目分析、未验证的破坏性改动）需主动隔离以保护真实仓库。

**两种 `working_dir` 下的 GitHub 协同衔接方式不同**：

| 情形 | mimo 写入位置 | 主Agent 如何提交 | 是否需要搬运 |
|---|---|---|---|
| 真实仓库（默认） | mimo 直接写真实工作副本，产物落在真实仓库目录内 | 主Agent 直接对该真实仓库 `git add <文件>` → `git commit` → `gh pr create` | 不需要，产物本就在真实仓库；提交前照常 review |
| 隔离沙箱（仅硬约束） | mimo 写 `<SANDBOX>`，真实仓库零接触 | 主Agent 先把经审核的沙箱产物**复制/移植**到真实仓库对应路径，再 `git add`/`commit` | 需要；搬运时只带经 review 的产物，不带沙箱测试垃圾 |

> 无论哪种情形，**真实 git/gh 动作始终由主Agent 执行**，mimo 只产出内容（代码 diff、提交信息、PR 描述）。选沙箱只是隔离"mimo 的写动作"，不改变"主Agent 独占 git"的边界；主Agent 执行 git 时须遵循路径核验防误报规范（先 `ls .git` 复核、用 `git -C "D:/绝对/Windows/路径"` 或先 cd /d/绝对/路径 再执行，禁止 `git -C /d/...`）。

**最小可用调用示例**（编写一段代码，两种形态的参数体相同；`working_dir` 默认填真实仓库目录，受硬约束时填 `<SANDBOX>`）：
```json
{
  "prompt": "请实现 Python 模块 validator.py：函数 validate_config(cfg: dict) -> tuple[bool, list[str]]，校验配置字典。只写这一个文件。",
  "working_dir": "<真实仓库目录，或受硬约束时的隔离沙箱 <SANDBOX>>",
  "format": "text",
  "skip_permissions": true
}
```

> 形态 A 调用时，将上述 `args` 体整体作为外层 `args` 字段的值：
> `{ "group": "<你的分组名>", "name": "mimo.code", "args": { "prompt": "...", "working_dir": "<真实仓库目录 或 <SANDBOX>>", "format": "text", "skip_permissions": true } }`

## 4. `continue_session`：先探测目标环境

实测经验（来自某次 Dynamic-mcp 代理配置）：在该环境下 `continue_session=true` 后 mimo 仍无上一轮记忆。但**其他环境可能不同**，切勿把"该开关无效"当作普适结论。标准做法：

1. 第 1 轮：正常提一个方案/任务，拿到 mimo 输出；
2. 第 2 轮：带 `continue_session=true` 追问"延续上文，补充…"，观察 mimo 是否接得上；
3. 若接得上 → 该环境支持会话保持，可酌情依赖；若接不上 → 该环境无状态，**所有多轮记忆由主Agent 在 `prompt` 中回灌**（格式见 `collab-workflow.md`）。
4. **无论环境如何，回灌都是最稳妥的兜底**，不依赖对环境开关的假设。

## 5. 健康检查（mimo.health，可选）

调用 `mimo.health` 可能返回底层配置（**以下为某次实测样本，不同接入可能不同，仅作排错背景**）：
- 默认模型：`mimo-v2.5`（对话可用变体如 `mimo-v2.5-pro`，但 `mimo.code` 走 `mimo run` 固定管线）；
- API 端点：某小米侧端点（如 `api.xiaomimimo.com/v1`）；
- 密钥来源：环境变量（如 `MIMO_API_KEY`），与主Agent 额度无关；
- 代码任务超时：某秒数（如 `300` 秒），单任务超过会超时失败。

健康检查用途：连接异常时先跑一次，确认 mimo 在线且密钥有效，再排除是代理层/传输层瞬时失联（见陷阱第 2 条）。

## 6. Token 消耗真相（重要，环境无关）

`mimo.code` 的返回中自带用量报告，形如：
```
输入 316 / 输出 104 / 推理 65 / 费用 $0
输入 167 / 输出 112 / 推理 57 / 费用 $0
输入 1325 / 输出 1409 / 推理 114 / 费用 $0   （代码审核长报告）
```

结论（对**任何**接入环境都成立）：
- **费用恒为 `$0`**：真正的推理（输出 token 生成、推理思考）全部由 MiMo 在**服务端**完成，使用的是服务端对应的额度（如 `MIMO_API_KEY`），**不消耗主Agent 的 LLM 额度**。
- **主Agent 仅承担"上下文成本"**：调用 mimo 时，只有"发给 mimo 的请求参数"和"mimo 返回的结果文本"会进入主Agent 的上下文窗口，按主Agent 供应商计费（算作主Agent 的**输入** token）。由于重活（长文/代码生成）由 mimo 承担，主Agent 自身的**输出生成 token 反而下降**。
- **唯一风险点**：mimo 返回的长文本（如 1409 token 的审核报告）会膨胀主Agent 上下文。在超长多轮讨论中，主Agent 应适时将"历史结论"压缩为摘要再回灌，避免上下文无限增长。

一句话总结：**调用 mimo.code 费主Agent 的"上下文"，不费主Agent 的"算力"。**

## 7. 典型调用模式速查

| 目标 | prompt 关键约束 | 是否写文件 |
|---|---|---|
| 编写新文件 | "请实现 X，只写这一个文件" | 是（新建） |
| 修改现有文件 | "请阅读 Y，定位问题并就地修复，保持签名不变，只修改此文件" | 是（修改） |
| 代码审核 | "请对 Z 做 code review，按严重度排序给出建议，不要改写文件" | 否（只读） |
| 项目分析 | "请分析目录结构/可维护性/风险，只分析不写文件" | 否（只读） |
| 方案/文档讨论 | "请提出技术路线/架构方案，只分析不写文件" | 否（只读） |
| 生成 GitHub 内容 | "请为本次变更写提交信息/PR 描述（不含真实 git 操作）" | 视阶段（通常只产出文本，由主Agent 落盘/提交） |
| 多轮迭代 | 每轮把"前几轮结论+待决问题"拼进 prompt 回灌 | 视阶段而定 |

## 8. 失败重试规范（强制连接韧性）

> **本规范与 SKILL.md「强制连接韧性约束」(★ 最高优先级) 一致，适用于两种接入形态（形态 A `Dynamic-mcp` 中转 / 形态 B MCP 直连）。** 现象背景：真实环境存在 `MiMo code` 与 `Dynamic-mcp` 的「代理重连波动」「MCP 工具偶发失联」。

任何**连接层**失败（尤其 `"Group not found"`、`MCP -32000 Connection closed`、原生 MCP 瞬时断连、TCP/HTTP 连接超时）**必须原样重试 2 次**（首次失败后再尝试 2 次，单次逻辑调用最多 3 次连接尝试），并保留原始参数。重试恢复率极高，且重试无副作用（mimo 调用是幂等任务描述，重复提交同一任务只会重新执行）。

**升级门禁**：仅当**连续 3 次连接超时/失联**（首次失败 + 2 次重试全失败，或跨调用累计 3 次连接失败事件）出现，才允许**主 Agent 单独工作**——放弃本轮对 `mimo.code` 的连接依赖，由主Agent 独立承接产出与决策；连接恢复后下一子任务重新尝试协同。

**计数器**：仅在连接层错误累加，一次成功连接即归零；非连接类错误（参数错误、内容分歧等）不计入。

若连续 3 次仍失败且需坚持协同：先跑一次 `mimo.health` 健康检查确认 mimo 在线与密钥有效，再排查网络/代理层；也可改用更短 prompt 降低单次负载，但仍受"重试 2 次 + 连续 3 次门禁"约束（重试仍须串行）。

## 9. 两种接入形态速查对照

| 维度 | 形态 A（Dynamic-mcp 工具中转） | 形态 B（MCP 服务方式直接连接） |
|---|---|---|
| 调用入口 | 动态工具调用（如 `call_dynamic_tool`） | 原生 MCP 工具（如 `mimo__code`） |
| 寻址方式 | 需带 `group` + `name: "mimo.code"` | 直接用工具名 |
| 参数体 | `args` 字段内嵌真实参数 | 直接传真实参数 |
| 探测手段 | `list_groups` / `get_dynamic_tools` | 查 MCP 工具列表 |
| 并行约束 | 同一分组内禁止并发 | 同一工具禁止并发 |
| 其余语义 | 与本技能完全一致 | 与本技能完全一致 |
