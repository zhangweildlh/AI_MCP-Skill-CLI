# 测试 / 验证矩阵（Test Matrix）

本文档给出全面验证 `mimo.code` 的用例矩阵，覆盖"通用性 + 协同充分性（讨论/审核/分工、双范式）+ 强制闭环防死锁 + 强制前置分析约束 + 强制连接韧性（重试 2 次 + 连续 3 次降级门禁）"五大目标。每个用例含：编号、目标、输入要点、预期结果、通过标准。实际执行遵循 SKILL.md 的"关键边界"与"强制连接韧性约束"——**串行调用 + 连接层失败强制重试 2 次 + 连续 3 次才降级主 Agent 单独工作 + working_dir 默认真实仓库（仅硬约束回退沙箱）+ 不依赖 continue_session**。

维度划分：
- **T-USE**：所有使用方法（参数组合，环境无关）
- **T-BND**：边界能力
- **T-CODE**：编程能力（单轮）
- **T-COORD**：协调编程闭环 + GitHub 协同闭环
- **T-DISC**：多轮讨论协同（范式A）+ 项目开发协同
- **T-PAR**：并行交叉审核（范式B）
- **T-LOCK**：强制闭环与防死锁验证
- **T-GATE**：强制前置分析约束（子任务启动闸门）验证

> `working_dir` **默认用真实仓库工作副本**（不用沙箱）；仅当受硬约束（mimo 部署强制沙箱、或高风险/边界探索性测试需主动隔离）时，回退**隔离沙箱占位 `<SANDBOX>`**，绝不指向含重要文件却未受控的目录。验证用例据此填写 `working_dir`。

## 维度一：所有使用方法（T-USE，5 例）

| 编号 | 目标 | 输入要点（prompt / args） | 预期结果 | 通过标准 |
|---|---|---|---|---|
| T-USE-01 | 纯生成（默认目录） | 仅 `prompt`："实现 foo.py"，不传 `working_dir` | 在代理默认目录生成文件 | 文件被创建且可运行；能定位到生成位置 |
| T-USE-02 | 指定目录写文件 | `working_dir`=`<SANDBOX>` + "只写 solver.py" | 文件落在指定目录 | 文件仅出现在 `working_dir`，不污染其他目录 |
| T-USE-03 | 返回格式 text vs json | 同任务分别 `format="text"` / `format="json"` | text 返回可读文本；json 返回结构化 | 两种格式均可解析；json 含预期字段 |
| T-USE-04 | 会话连续性探测 | 第1次提方案 A；第2次带 `continue_session=true` 追问"延续上文" | **记录该环境是否保活**（可能接上也可能接不上） | 明确结论：该环境 `continue_session` 生效/不生效；据此决定回灌策略 |
| T-USE-05 | 权限开关 | `skip_permissions=true` vs 不传，执行写文件任务 | 传 true 不挂起直接完成 | 非交互场景必须设 true；不传可能交互挂起 |

## 维度二：边界能力（T-BND，7 例）

| 编号 | 目标 | 输入要点 | 预期结果 | 通过标准 |
|---|---|---|---|---|
| T-BND-01 | prompt 超长（>7000 字） | 塞入大段背景+多文件要求的超长 prompt | 正常接收并完成（或合理裁剪） | 不崩溃；输出与 prompt 关键约束一致 |
| T-BND-02 | 空/极短 prompt | prompt="写代码" / "" | 返回澄清或最小合理实现 | 不报错退出；有明确反馈 |
| T-BND-03 | 目录不存在 | `working_dir` 指向不存在路径 | 自动创建目录或明确报错 | 行为可预期；不静默失败 |
| T-BND-04 | 目录只读 | `working_dir` 设为只读目录 + 写文件任务 | 写失败有明确错误，不破坏目录 | 错误信息可诊断 |
| T-BND-05 | 任务超时（>300s） | 要求生成超大型项目（触发超时） | 超时失败 | 返回超时错误而非无限挂起；可重试/拆分 |
| T-BND-06 | 中英文混合 prompt | 中英混杂的技术要求 | 正确理解和执行 | 输出符合混合语义 |
| T-BND-07 | 大项目分析 | 对整个仓库做结构/风险分析 | 给出概览（可能省略细节） | 不 OOM/不超时；结论有结构 |
| T-BND-08 | **连接韧性（代理重连波动 / MCP 偶发失联）** | 注入 1~3 次 `Group not found` / `MCP -32000` / 连接超时，验证重试与降级门禁 | 第 1~2 次失败被重试吸收恢复；连续 3 次失败触发主 Agent 单独工作 | 失败先**原样重试 2 次**；计数器仅对连接层错误累加、成功即归零；非连接错误不计入；连续 3 次才降级，降级后主 Agent 自审自验、连接恢复后重新协同 |

## 维度四：协调编程与 GitHub 协同（T-COORD，2 闭环）

| 编号 | 目标 | 流程 | 通过标准 |
|---|---|---|---|
| T-COORD-01 | 编码协同闭环（范式A：设计→实现→审查+新版本→修订） | ①主Agent 给精确规格(v1) → ②mimo 实现(v2) → ③主Agent 审查出具【审核报告+v3 指示】 → ④mimo 修订(v4) → ⑤主Agent 读回验证（≤5 轮） | 每轮接收方产「审核报告+新版本」；最终文件通过主Agent 全部自测；全程串行 |
| T-COORD-02 | GitHub 协同闭环（范式B 搜索 + 范式A 审阅 + 主Agent 真实执行） | ①主Agent 建/切分支（gh/git）→ ②范式B：主Agent `gh` 搜索 + mimo 联网调研并行，交叉互审 → ③mimo 在 `<SANDBOX>` 生成代码变更 + 提交信息文本(v2) → ④主Agent `git commit`/`gh pr create` → ⑤主Agent 拉 diff 交 mimo 审(范式A, v4…) → ⑥主Agent `gh pr merge`（Review 无 P0 后） | mimo 仅产出内容；真实 git/gh 全由主Agent 执行；范式B 交叉审核与范式A 修订均收敛 |

> T-COORD-02 是**设计形态**（mimo 不直接 git，主Agent 执行外部动作），首次使用按此流程实测一遍以确认本环境行为。

## 维度五：多轮讨论与项目开发协同（T-DISC，范式A，2 迭代）

| 编号 | 目标 | 流程 | 通过标准 |
|---|---|---|---|
| T-DISC-01 | 讨论协同（范式A：v1→v2→v3→v4 串行交替审核） | ①主Agent 提 v1（背景+路线/方法/构架/代码）→ ②mimo 出【审核报告+v2】 → ③主Agent 出【审核报告+v3】 → ④mimo 出【审核报告+v4】…（每轮"只分析不写文件"，≤8 轮） | 每轮接收方均产出「审核报告+新版本」；mimo 各轮产出连贯（因主Agent 回灌）；最终一致方案；原项目零接触 |
| T-DISC-02 | 项目开发协同（编排流水） | 主Agent 编排：需求澄清（讨论·范式A）→ 方案定稿（讨论·范式A 收敛）→ 调研搜索（GitHub·范式B）→ 编码实现（编码·范式A）→ 提交与 PR（GitHub）→ Code Review（GitHub·范式A）→ 合入 → 回归/重构（编码·范式A） | 每个子环节各自遵守闭环元规则（出口条件+最大轮次+三要素）；整体由主Agent 把控推进 |

## 维度六：并行交叉审核（T-PAR，范式B）

| 编号 | 目标 | 流程 | 通过标准 |
|---|---|---|---|
| T-PAR-01 | 并行调研搜索交叉互审 | ①主Agent 与 mimo **并行**开展不同子任务（主Agent 跑 `gh`/本地工具搜索，mimo 跑联网搜索/方案草拟，均只分析不写文件）→ ②双方各自产出中间产物 → ③交叉灌注：主Agent 产物给 mimo 审、mimo 产物给主Agent 审 → ④各自出审核报告 → ⑤主Agent 合成最终方案 | 双方确实并行（主Agent 真实执行外部搜索，mimo 产出可复核文本）；交叉审核产生互补/修正信息；主Agent 合成闭环 |
| T-PAR-02 | 并行方案提报交叉互审 | ①主Agent 与 mimo 各自独立起草一份方案（不同角度）→ ②交叉灌注互审 → ③各自出审核报告，指出对方遗漏/风险 → ④主Agent 综合双方长处合成最终方案 | 两份独立方案均有实质内容；互审发现彼此盲点；合成方案优于任一方单独方案 |
| T-PAR-03 | 范式B 批次上限 | 故意推进 6 个范式B 批次 | 触及上限（≤5）即终止 | 不无限并行；超限转入仲裁或落盘 |

> 范式B 关键约束：mimo 不直接 git/gh；涉及真实外部操作（如 `gh` 搜索、git 提交）由主Agent 执行，mimo 只产出可被主Agent 复核的内容。

## 维度七：强制闭环与防死锁（T-LOCK）

| 编号 | 目标 | 输入要点 | 预期结果 | 通过标准 |
|---|---|---|---|---|
| T-LOCK-01 | 出口条件显式化 | 每个协同任务启动即声明 Done Criteria | 任务有明确终止定义 | 无"无尽头讨论"；达成即落盘 |
| T-LOCK-02 | 最大轮次硬上限 | 编码协同故意迭代到 6 轮 / 讨论协同到 9 轮 / 范式B 到第 6 批次 | 触及上限即终止 | 编码 ≤5、讨论 ≤8、范式B 批次 ≤5；超限不继续循环 |
| T-LOCK-03 | 停滞检测触发 | 构造"mimo 连续 2 轮输出高度相似 / 主Agent 重复同一意见 / 范式B 交叉审核无互补信息" | 触发死锁判定 | 连续 2 轮/批次无进展即识别，不傻循环 |
| T-LOCK-04 | 死锁仲裁升级 | 触发 T-LOCK-03 后，主Agent 必须（拍板 或 交用户 或 降级单轮） | 强制出口 | 绝不无限循环；分歧点被总结并裁决/上报 |

## 维度八：强制前置分析约束验证（T-GATE）

> 验证 v4 新增的「子任务启动闸门」本身是否被遵守——不仅验证协同结果，也验证"开工前的判定动作"是否发生、是否记录。

| 编号 | 目标 | 流程 / 输入要点 | 通过标准 |
|---|---|---|---|
| T-GATE-01 | 未判定即开工应被拦截 | 故意在主Agent 开展某子任务（如编码实现）前，跳过"分析→判定→执行"闸门直接发 `mimo.code` 调用 | 主Agent 自检发现"未走闸门"，先补判定（场景+范式）再开工；不出现"先动手后补范式" |
| T-GATE-02 | 复合任务每步独立判定 | 项目开发协同流水：需求澄清→方案→调研→编码→PR→Review→合入→回归，检查每一步是否各自走闸门 | 每一步都有独立的"场景+范式"判定结论，未用任务级统一判定替代单步判定 |
| T-GATE-03 | 判定结论完整记录 | 每步开工前是否显式记录（适用场景 + 适用范式） | 判定结论可回溯（场景+范式均落记录），不遗漏 |
| T-GATE-04 | 场景与范式归属正确 | 分析步定"性质+场景"、判定步定"范式"，二者不混写 | 场景在①分析步确定、范式在②判定步确定；无重复/错位 |

## 执行纪律（务必遵守）

1. **串行**：所有 `mimo.code` 调用**逐次发起**，不得并发。（范式B 的"并行"是主Agent 与 mimo 承担**不同子任务**的并行，各自仍单次串行调用 mimo。）
2. **重试**：任一调用返回 `"Group not found"` / `MCP -32000` / 原生 MCP 断连 / 连接超时等**连接层错误**，必须**原样重试 2 次**（共最多 3 次连接尝试）；仅连续 3 次连接失败才允许主 Agent 单独工作（降级门禁）。
3. **隔离（仅硬约束时）**：`working_dir` **默认用真实仓库工作副本**，不隔离；仅当受硬约束（mimo 部署强制沙箱、或高风险/边界探索性测试）才用独立沙箱 `<SANDBOX>`，且只读分析任务更要显式"只分析不写文件"。
4. **回灌**：多轮中每轮 `prompt` 必须包含前几轮结论（含「审核报告 + 上一版本」，见 `collab-workflow.md` 第 3 节），不依赖 `continue_session`。
5. **范式择用（按子任务动态择范）**：**不对整个任务固定一个范式**，而在每个子任务启动时按性质选——编码/讨论/文件类子任务用范式A（每轮产出审核报告+新版本）；可分解探索类子任务（搜索/调研/方案提报）用范式B（并行后交叉互审）；复合子任务（如 GitHub 协同）分段混合（搜索范式B、实现/Review 范式A）。
6. **防死锁**：每条协同启动时声明出口条件、遵守最大轮次、每轮判定收敛；连续 2 轮/批次无进展即仲裁（拍板/交用户/降级），**绝不无限循环**。
