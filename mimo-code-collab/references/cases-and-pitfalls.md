# 实测案例与陷阱速查（Cases & Pitfalls）

本文档汇总对 `mimo.code` 的**真实实测**结论与陷阱。所有"实测"均来自实际调用；标注"设计形态"的为例证模板，首次使用应按其实测一遍。全文**不绑定任何本机路径/分组名/连接器名**，可直接移植到其他接入了 `mimo.code` 的 Agent。

> 注：v5 起 `working_dir` 策略改为"默认真实仓库、仅硬约束回退沙箱"；下方案例在历史沙箱环境下实测，结论仍然有效，迁移到真实仓库时按 `invocation.md` 第 3.1 节衔接即可。

---

## 一、关键陷阱速查表

| # | 症状（实测出现） | 根因 | 对策 |
|---|---|---|---|
| 1 | **并行**发多个 `mimo.code` 调用，全部返回 `"Group not found"`（或原生 MCP 类似错误） | 对 mimo 的并发不支持（代理端瞬时竞态或 MCP 串行约束） | **严格串行**调用；实测串行成功率 100%。范式B 的"并行"是主Agent 与 mimo 承担不同子任务，各自仍单次串行调 mimo |
| 2 | 单次调用返回 `"Group not found"` / `MCP -32000 Connection closed` / 原生 MCP 瞬时断连 | 传输层/代理冷启动瞬时失联 | **原样重试 1 次**，多数立即恢复；不要立刻改参数 |
| 3 | 设 `continue_session=true` 后，mimo 说"没有上一轮上下文" | **是否保活因环境而异**（某次代理配置下不保活，其他环境可能支持） | 先按 `invocation.md` 第 4 节**探测目标环境**；无论环境如何，**主Agent 在 prompt 中回灌历史都是最稳妥兜底** |
| 4 | 讨论/分析任务，mimo 却改写了文件 | mimo 默认会动 `working_dir` 内文件 | `prompt` 显式写"只分析、不写任何文件 / 不要改写文件" |
| 5 | 多轮后主Agent 上下文被超长返回（如 1409 token 审核报告）撑爆 | mimo 长返回进入主Agent 上下文 | 回灌时把历史**压缩为结论摘要**；非必要不重复长文 |

> **Token 真相（环境无关，对一切接入都成立）**：mimo 返回自带用量报告（输入/输出/推理/费用），**费用恒为 `$0`**。真实推理由 MiMo 在**服务端**完成（使用服务端对应的额度，如 `MIMO_API_KEY`），**不消耗主Agent 额度**；主Agent 仅承担"请求+返回"的上下文（输入）成本。详见 `invocation.md` 第 6 节。

## 二、实测案例一：编码协同闭环（范式A，validator.py）

**目标**：验证"主Agent 设计(v1) → mimo 实现(v2) → 主Agent 审核并出【审核报告+v3 指示】 → mimo 修订(v4)"的串行交替审核闭环（在隔离沙箱 `<SANDBOX>` 内）。

**步骤与结果**：
1. **设计（主Agent → v1）**：给出精确规格——`validate_config(cfg: dict) -> tuple[bool, list[str]]`，校验 `name`(非空字符串) 与 `version`(语义化版本)，失败返回 `(False, 错误列表)`；要求类型注解、中文注释、`__main__` 自测；"只写这一个文件"。
2. **实现（mimo → v2）**：在沙箱生成 `validator.py`，7 个自测用例通过，质量良好。
3. **审查（主Agent → 审核报告 + v3 指示）**：读回发现真实缺陷——当 `cfg` 非字典（如 `None`/列表）时，首行 `if "name" not in cfg` 会抛 `TypeError`，**缺少输入类型防护**。出具审核报告并指明修订点。
4. **修订（mimo → v4）**：回灌规格 + 缺陷描述，要求"函数开头加 `if not isinstance(cfg, dict): return (False, ["cfg 必须是字典类型"])`；`__main__` 补 `cfg=None` 用例；保持签名不变；只修改此文件"。mimo 返回修订后代码 + 修订说明。
5. **验证（主Agent）**：读回确认防护已加、`cfg=None` 用例已补，8 用例通过。

**结论**：编码协同范式A 闭环成立——每轮接收方都产出「审核报告 + 新版本」，mimo 能准确理解审查意见并定点修订。

## 三、实测案例二：讨论协同多轮（范式A 串行交替审核，<示例项目> 移植）

**目标**：验证主Agent 与 mimo 能否以"v1→v2→v3→v4 串行交替审核"范式多轮讨论可行性/技术路线/架构并形成唯一一致方案。以某"源项目 → 目标平台网页版移植"为背景（代指真实工程 `<示例项目>`）。

**约束遵守**：`<示例项目>` 全程仅被只读列举**一次**，未读取内容、未写入、未移动任何文件；所有 mimo 调用 `working_dir` 均用隔离沙箱 `<SANDBOX>`。

**步骤与结果**：
1. **第1轮（主Agent → v1）**：prompt 要求提 3 条技术路线（A. API 代理桥接 / B. 纯提示词工程 / C. 本地中间层服务），"只分析不写文件"。mimo 返回 3 路线 + 对比表（核心思路/适用场景/主要风险），质量高。
2. **第2轮（探测 continue_session）**：带 `continue_session=true` 追问比选 → 该环境下 mimo 回复"没有上一轮上下文"。**→ 记录该环境无状态，后续全靠回灌**（其他环境可能不同，见陷阱 #3）。
3. **第3轮（mimo → 审核报告 + v2）**：回灌"背景回顾（3 路线评估结论）+ 决策（B 为主、C 为补充）"，要求"先给 v1 的【审核报告】，再产出【v2 架构草图】"。mimo 返回：审核报告（含 B 受上下文长度与会话持久化限制等风险）+ 完整模块架构（目录结构 + 模块职责 + 下沉能力 + 路由伪代码）。
4. **第4轮（主Agent → 审核报告 + v3）**：主Agent 审阅 v2 架构，出具审核报告（指出"本地中间层状态管理缺持久化方案"），产出 v3（补充持久化与回退策略）。回灌 mimo。
5. **第5轮（mimo → 审核报告 + v4）**：mimo 审核 v3，确认无新增异议，微调后给 v4 一致草图。
6. **结果**：多轮交替审核在"主Agent 回灌"机制下连贯可行，最终形成唯一一致架构方案。

**结论**：讨论协同范式A 经实测成立——"你出 v1、我审并出 v2；我审并出 v3、你审并出 v4；循环至一致"范式可行，收敛由主Agent 回灌 + 显式出口条件保证。

## 四、设计形态案例三：GitHub 协同（范式B 搜索 + 范式A 审阅 + 主Agent 真实执行）

> 本案例为**设计形态**（mimo 不直接 git，首次使用应按此实测一遍以确认本环境行为）。核心边界：**真实 git/gh 动作由主Agent 执行，mimo 只产出内容。**

**典型流水**（以"修复一个 BUG 并开 PR"为例）：
1. **主Agent**：`gh`/`git` 建分支、切到修复分支（真实外部操作，主Agent 独占）；
2. **范式B 调研**：主Agent 用 `gh search`/本地工具搜索相关上下文，mimo 并行联网搜索同类修复方案（只分析），交叉互审后主Agent 合成调研结论；
3. **mimo（范式A 实现 v2）**：在 `<SANDBOX>` 生成修复代码 + 产出提交信息文本（prompt："请修复 X，并给出符合约定式提交的提交信息，不要执行任何 git 命令"）；
4. **主Agent**：`git add` + `git commit`（用 mimo 产出的提交信息）+ `gh pr create`（用 mimo 产出的 PR 描述）；
5. **主Agent + mimo（范式A Review）**：拉取 PR diff 交 mimo 审（prompt："请 Review 以下 diff，按 P0–P2 排序给出意见，只输出意见文本"），主Agent 出具审核报告；
6. **主Agent**：若 Review 无 P0，则 `gh pr merge` 合入；否则回灌意见交 mimo 修订（编码协同闭环）。

**出口条件**：PR 已开、diff 经 mimo 审阅无 P0、主Agent 已合入。**同样受最大轮次与死锁仲裁约束**（见 `collab-workflow.md` 第 2 节）。

## 五、设计形态案例四：并行交叉审核（范式B，调研搜索）

> 本案例为**设计形态**（验证范式B），首次使用按此实测一遍以确认本环境行为。

**典型流水**（以"评估某技术方案的可行性"为例）：
1. **并行开展**：主Agent 执行 `gh search code "关键词"` 取仓库内相关实现；同时 mimo 并行联网搜索业界同类方案（prompt："只分析不写文件，产出可复核的调研笔记"）；
2. **交叉互审**：主Agent 把 `gh` 结果给 mimo 审（"请审核以下搜索结论，指出遗漏/风险"）；mimo 把调研笔记回灌主Agent 审；
3. **各自出审核报告**：主Agent 指出 mimo 联网结论中"未贴合本仓库实际约束"的点；mimo 指出主Agent `gh` 搜索"遗漏了上游仓库的同类实现"；
4. **合成闭环**：主Agent 汇总双方审核报告，合成"可行性结论 + 推荐实现路径" → 落盘。

**边界**：`gh` 搜索与任何真实 git 动作为主Agent 独占；mimo 只产出可被主Agent 复核的文本。范式B 单次并行 + 一轮交叉审核即一个批次，总批次 ≤ 5。

## 六、给"未来的自己"的速记

1. 第一次用 `mimo.code`：**先探测接入形态**（形态A：Dynamic-mcp 中转用 `list_groups`；形态B：MCP 服务直连查工具列表）→ 读本技能 SKILL.md → 再动手。
2. 三要素贯穿任一任务：**讨论 + 审核 + 分工**；能力边界/权限约束之外（真实 git/gh、本地编译测试、私有凭据操作）一律由主Agent 完成。
3. 双范式**按子任务性质动态择用**：**范式A（串行交替审核）**用于编码/修改/BUG 修复/方案讨论/文件编写——每轮接收方都出「审核报告 + 新版本(v2/v3/v4…)」；**范式B（并行交叉审核）**用于 GitHub 搜索/联网搜索/思考/方案提报——双方并行后交叉互审。**不固定整个任务用一个范式**，每个子任务启动时独立判定。
4. 调 `mimo.code` 永远**串行**（对 mimo 的并发全失败）；报错先**重试 1 次**。
5. 多轮讨论 = 主Agent 当"记忆载体"，每轮把"审核报告 + 上一版本"塞进 prompt（兜底，不依赖 `continue_session`）。
6. GitHub 协同里，**mimo 只写内容、主Agent 才碰 git/gh**。
7. 每一份协同都先声明出口条件、守住最大轮次；连续 2 轮/批次无进展就**仲裁**（拍板/交用户/降级），绝不无限循环。
8. 别怕让 mimo 干重活：它的推理免费（对主Agent 而言），主Agent 只付"上下文"的账。
