# 协同工作流详解（Collaboration Workflow）

本文档是 `mimo.code` 协同能力的核心。它回答：**主Agent 如何与 mimo.code 在任意工程任务上像两名工程师一样讨论、相互审核、分工修订，并且每一份协同都具备强制闭环、不会无限死锁。**

> 适用前提：mimo.code 是**代码/文本智能体**，作用域限于 `working_dir` 内文件读写与技术讨论；它**不直接操作 GitHub/git/外部系统**。所有真实 git/gh 动作由**主Agent 执行**。本技能把二者组织成"通用分工闭环 + 双范式"。

---

## 1. 协同范式总览：双角色模型与三要素

### 1.1 双角色模型
| 角色 | 职责 | 掌握的权力 |
|---|---|---|
| **主Agent（本地主编/架构师/执行者）** | 提需求与方向、审核 mimo 产出、做最终决策、对外部系统（git/gh/文件系统之外）执行真实动作 | **决策权** + **外部系统操作权** + **记忆权**（回灌上下文） |
| **mimo.code（远程协作者）** | 在 `working_dir` 内生成/修改/分析代码与文件、做技术讨论、产出内容（含 GitHub 文案） | 仅"内容/代码产出权" |

核心原则：**主Agent 永远掌握决策与外部操作；mimo 是产出方，不替主Agent 拍板、不碰 git。能力边界与权限约束之外的工作由主Agent 完成。**

### 1.2 三要素（贯穿任一任务，不分协同类型）
- **讨论（Discussion）**：任何一方都可提出观点、方案、疑问、替代路线。不是"一方命题、另一方被动答"，而是双向往复。
- **审核（Review）**：任何一方收到对方（或交叉收到）的产出物后，都必须给出**详细的审核报告**（覆盖可行性 / 风险 / 不足 / 与约束契合度）。在串行范式（范式A）下，审核方同时产出"新版本产出物"。
- **分工（Division）**：主Agent 掌决策与外部操作；mimo 掌内容/代码产出。**边界外由主Agent 完成**——真实 git/gh、需本地环境的编译/测试、涉及私有凭据的操作等。

### 1.3 双范式（按子任务性质动态择用，而非对整个任务固定）
- **范式A — 串行交替审核（Serial Alternating Review）**：逐轮打磨、收敛到唯一方案。每轮接收方产出「审核报告 + 新版本产出物」（v1→v2→v3→v4…）。适用于编码、修改、BUG 修复、方案/架构讨论、文件/文档编写。
- **范式B — 并行交叉审核（Parallel Cross Review）**：双方并行承担不同子任务，产出物交叉互审。适用于 GitHub 仓库搜索、联网搜索、问题思考、方案提报等可分解探索任务。

> **关键：范式选择的粒度是「子任务」，不是「整个任务/项目」**。一个项目含多种性质的多个子任务，应在**每个子任务启动时按性质重新选范式**，而非对整个项目固定选一个。复合任务（如 GitHub 协同）内部不同阶段可分别选 A/B。

### 1.4 判定方法：动态择范决策流程（用于 1.5 第②步）
> **⚠️ 强制约束**：以下决策是「强制前置分析约束（1.5 三步走闸门）」中第②步「判定」环节的核心动作，**必须完成**。每一个任务 / 子任务 / 子步骤 / 子流程正式开工之前，主Agent **必须**先走完这个决策流程并得出"适用范式"的明确结论，**未判定不得开工**；判定结论（场景 + 范式）应在协同时显式记录。复合任务里的每一步都要重新判定，不能用"整个任务选了一个范式"替代单步判定。

对每个子任务，先回答一个问题，再定范式：
```
问：这个子任务是要"收敛成一份唯一交付"，还是"可并行铺开做调研/搜索/生成"？
├─ 收敛成唯一交付（代码/方案/文档需逐轮审改定稿）        → 范式A（串行交替审核）
├─ 可并行铺开调研/搜索/提报（子任务彼此独立）            → 范式B（并行交叉审核）
└─ 复合子任务（如 GitHub：搜索+实现+Review）             → 分段选：搜索用范式B，实现/Review 用范式A
```
> 示例（项目开发协同编排流，见 4.4）：需求澄清(范式A) → 方案定稿(范式A) → 调研搜索(范式B) → 编码实现(范式A) → 提 PR/Review(GitHub 混合：搜索范式B、审改范式A) → 合入 → 回归(范式A)。每一步都按自身性质独立择范、独立走闸门。

### 1.5 强制前置分析约束（三步走闸门）
把 1.4 的决策流程进一步固化为**不可跳过的主Agent 动作**，在每个子任务/子步骤/子流程启动前机械执行：

| 步骤 | 动作 | 产出 |
|---|---|---|
| **① 分析（Analyze）** | 归类该子任务的性质——"收敛型"（需逐轮打磨出唯一交付）还是"铺开型"（可并行调研/搜索/生成）；并归其所属协同场景（编码 / 讨论 / GitHub / 项目开发） | 性质标签 + 场景标签 |
| **② 判定（Decide）** | 依上一步的分析结论，显式确定**适用范式**（A 串行 / B 并行 / 分段混合；具体范式择用方法见第 1.4 节） | 范式结论（须记录，连同①的场景标签共同构成"场景 + 范式"判定结论） |
| **③ 执行（Execute）** | 严格按判定的"场景 + 范式"正式开展工作，套用对应协同模板，并全程遵守第 2 节闭环元规则 | 受约束的协同产出 |

**强制要点（不允许例外）**：
- 判定必须在"开工动作"之前完成，严禁"先动手再补范式"；
- 复合任务中**每一步/子步骤都要独立走完 ①②③**，不得用任务级统一判定替代单步判定；
- **范式内部的逐轮迭代不重复走闸门**：范式A 的 v1→v2→v3… 与范式B 的并行批次推进，都属于同一子任务内部的收敛/探索过程，不每轮重走闸门；闸门只在"进入新子任务"或"切换子任务性质"时各走一次；
- 此判定是主Agent 的责任，mimo 不参与、只承接判定后的产出工作。

## 2. 强制闭环元规则（★ 防死锁，每条协同必须守住）

每一份协同任务启动即须满足以下四条，**缺一不可**。这是回答"是否有强制闭环、是否会死锁"的关键。

### 2.1 出口条件（Done Criteria）显式化
启动协同时，**先声明"什么算完成"**，例如：
- 编码协同："文件通过主Agent 全部自测，且覆盖边界用例"；
- 讨论协同："双方对技术路线/实现方法/架构/代码四要素无新增异议"；
- GitHub 协同："PR 已开、diff 经 mimo 审阅无 P0、主Agent 已合入"；
- 范式B 探索："双方产出物经交叉审核补齐彼此遗漏，主Agent 合成最终方案"。

### 2.2 最大轮次硬上限
- **编码协同**（范式A 设计→实现→审查→修订）：≤ **5 轮**；
- **讨论协同**（范式A v1/v2/v3… 比选）：≤ **8 轮**；
- **范式B**：单次"并行 + 一轮交叉审核"算一个批次，总批次 ≤ **5**；
- 触及上限即终止循环，转入 2.4 仲裁。

> **复合任务的整体轮次说明（D7）**：最大轮次上限是**按子任务类型分别计**的（编码子任务 ≤5、讨论子任务 ≤8、范式B 子任务 ≤5 批次），**复合任务没有"全局单一轮次上限"**——它由各子任务各自守住自身上限、再由第 2.4 节仲裁把握整体推进，而非把全流程累计成一个大轮次。某子任务触顶即在其内部仲裁落盘，不阻塞其他子任务。

### 2.3 停滞检测（死锁判定）
连续 **2 轮/批次**满足任一即判定"陷入死锁"，必须触发仲裁：
- mimo 输出与上一轮**核心方案高度相似**（未产生新信息）；
- 主Agent **重复同一审查意见**（mimo 未实质响应）；
- 分歧集合**大小未缩小**（多轮后仍卡在同一批待决点）；
- 范式B 中：双方交叉审核后**未产生任何互补/修正信息**，仅互相确认无意见。

### 2.4 死锁仲裁与升级（强制出口，绝不无限循环）
触发 2.3 时，主Agent **必须**执行以下之一，不得继续无谓讨论：
1. **主Agent 拍板**：总结分歧点，明确裁决选一个方案/路线，落盘推进；
2. **交用户决策**：用 `AskUserQuestion` 把分歧点呈给用户，按回复推进；
3. **降级为单轮执行**：放弃协同比选，主Agent 直接给出指令让 mimo 按既定方向实现。

> 一句话：**闭环的终点是"达成一致"或"主Agent/用户裁决"，不是"一直讨论到天荒地老"。**

## 3. 会话回灌格式（兜底记忆机制）

由于 `continue_session` 是否保活因环境而异（见 `invocation.md` 第 4 节），**最稳妥的兜底**是主Agent 在每轮把历史拼进 `prompt`。在双范式下，回灌须明确携带"上一轮审核报告 + 上一版本产出物"。推荐固定格式：

```
（背景回顾：<项目目标 + 前几轮已达成的事实/决策摘要，3–6 句>）
（上一轮要点：<mimo 上一轮输出的核心结论 / 或主Agent 上一轮审核报告摘要>）
（上一版本产出物：<vN 的关键内容，或指明已落盘的文件路径>）
（待决问题：<本轮需要对方回答/决策的具体点>）
请基于以上背景，<本轮任务：提出 vN+1 / 审核 vN 并产出 vN+1 / 比选路线 / 生成 GitHub 内容 / 实现某文件>。
<约束：只分析不写文件 / 或 只写某指定文件>。
```

**要点**：
- 背景回顾要"增量压缩"——越往后的轮次，越把早期细节压成结论，只保留影响当前决策的事实，避免 prompt 无限膨胀（也控制主Agent 上下文成本）；
- 待决问题要具体、可判定，不要开放到对方无从下手；
- 范式A 中每轮都把"审核报告 + 新版本"显式标注（如 `【审核报告】…【v3 产出物】…`），便于下一轮回灌。

## 4. 四类协同工作流模板

### 4.1 编码协同（编写 / 修改 / BUG 修复）— 范式A
**主Agent 出题 + 审查，mimo 实现 + 修订**。每轮接收方产出「审核报告 + 新版本」。

1. **设计（主Agent → v1）**：写出精确规格（函数签名、输入/输出、约束、边界用例），作为 `prompt` 交 mimo，`working_dir`=沙箱（受硬约束时的隔离选项；v5 起默认真实仓库工作副本）；
2. **实现（mimo → v2）**：`prompt` 含"只写 X 文件" + `skip_permissions=true`；mimo 返回代码 + 简短说明；
3. **审查（主Agent → 审核报告 + v3 指示）**：主Agent 读回文件、跑自测、找出缺陷（类型防护、边界、异常路径），出具**审核报告**并指明修订点，作为新 `prompt` 回灌（规格 + 缺陷 + "只修改此文件，保持签名"）；
4. **修订（mimo → v4）**：mimo 返回修订后代码 + 修订说明；
5. **验证（主Agent）**：读回确认修订落地、自测通过 → 满足出口条件即闭环。
> 已实测跑通：主Agent 设计 `validate_config` 规格(v1) → mimo 实现(v2) → 主Agent 审查发现"cfg 非字典缺类型防护"(审核报告+v3指示) → mimo 修订加防护(v4) → 验证通过。

### 4.2 讨论协同（方案 / 架构 / 文件 / 文档）— 范式A
**双方交替提出带「审核报告 + 新版本」的方案**，收敛到唯一交付。

**第①轮（主Agent → v1 产出物）**
```
（背景：<项目目标与约束>）
这是我提出的 v1 方案：
- 技术路线：<...>   - 实现方法：<...>
- 关键实例：<...>   - 程序架构：<目录 + 模块职责>
- 草拟代码：<核心片段>
请只分析，不写任何文件。
```
**第②轮（mimo → 审核报告 + v2 产出物）**
```
（背景回顾：<项目目标>）（v1 要点：<路线/方法/构架/代码摘要>）
请基于 v1 给出【审核报告】（可行性/风险/不足/与约束契合度），并产出你的【v2 修订/替代方案】
（技术路线、实现方法、实例、构架、关键代码）。只分析，不写任何文件。
```
**第③轮（主Agent → 审核报告 + v3 产出物）**
```
（背景回顾：<目标>）（mimo 的 v2 审核报告摘要：<...>）（v2 要点：<...>）
【我的审核报告】：<v2 的不足/风险/可改进点>
【v3 产出物】：在 v2 基础上修订后的方案（路线/方法/构架/代码）。只分析，不写任何文件。
```
**第④轮（mimo → 审核报告 + v4）**：重复"回灌历史 + 要求审核并产出下一版"，直到双方无新增异议 → 落盘唯一方案。
> 收敛判据（出口条件）：双方对"技术路线、实现方法、程序架构、关键代码"四要素均无新增异议；或已达成明确取舍决策且 mimo 能产出一致草图。连续 2 轮无进展即触发 2.4 仲裁。

### 4.3 GitHub 协同（内容生成 + 主Agent 真实执行）— 范式B + 范式A
**关键边界**：mimo **不直接 git/gh**。真实动作（commit/push/开 PR/merge、以及 `gh` 仓库搜索）由**主Agent 执行**；mimo 只产出"写什么内容"。

**阶段一 · 搜索/调研（范式B 并行交叉）**
1. 主Agent 与 mimo **并行**开展：主Agent 用 `gh`/本地工具搜索目标仓库/代码/历史 PR；mimo 并行做联网搜索/对照方案草拟（prompt："只分析不写文件，产出可复核的调研笔记"）；
2. 交叉灌注：主Agent 的搜索结果给 mimo 审（"请审核以下 `gh` 搜索结论，指出遗漏/风险"）；mimo 的调研笔记给主Agent 审；
3. 各自出审核报告，主Agent 合成调研结论。

**阶段二 · 实现与审阅（范式A 串行交替）**
| 子环节 | 主Agent | mimo.code |
|---|---|---|
| 变更实现 | 建/切分支（gh/git） | 在 `working_dir` 生成/修改代码（v2） |
| 提交 | 用 mimo 产出的提交信息 `git commit` | 生成提交信息文本（v2 内容） |
| 开 PR | `gh pr create`（用 mimo 产出的 PR 描述） | 生成 PR 描述/标题文本（v2 内容） |
| Code Review | 拉取 diff 交 mimo 审 → 主Agent 出审核报告 | 对 diff 给出 Review 意见（P0–P2 排序，v2/v4…） |
| 合入 | `gh pr merge`（Review 无 P0 后） | — |

闭环：mimo 产出内容 → 主Agent 执行 git/gh → mimo 审 diff（范式A）→ 主Agent 合入。同样受 2.2/2.3/2.4 约束。

> **`working_dir` 与提交的衔接（D1 策略）**：本技能**默认直接用真实仓库**作为 `working_dir`——此时 mimo 直接写入真实工作副本，主Agent 直接对该仓库 `git add`/`commit`/`gh pr create` 即可，**无需搬运**。仅当受硬约束（mimo 部署强制 `<SANDBOX>`、或安全策略禁止直写真实仓库、或高风险探索性测试）时回退沙箱：mimo 写 `<SANDBOX>`，主Agent 把**经审核**的沙箱产物移植到真实仓库后再提交，避免带入沙箱测试垃圾。无论哪种情形，"mimo 只产出内容、主Agent 独占 git"的边界不变（详见 `invocation.md` 第 3.1 节）。

### 4.4 项目开发协同（编排以上三类）— 按子任务动态择范（范式A + 范式B 混合）
主Agent 当编排者，把一次完整开发串成流水；**流水中的每一步都是一个独立子任务，在开工前必须按第 1.4 / 1.5 节"强制前置分析约束"单独走闸门（分析→判定→执行），再正式开展**，而非对整个项目套用单一范式：
```
需求澄清（讨论协同·范式A）→ 方案定稿（讨论协同·范式A 收敛）→
调研搜索（GitHub 协同·范式B 并行）→
编码实现（编码协同·范式A，可多模块拆分）→
提交与 PR（GitHub 协同）→ Code Review（GitHub 协同·范式A）→ 合入（主Agent）→
回归/重构（编码协同·范式A）→ 发布文案（GitHub 协同内容生成）
```
每个子环节各自遵守第 2 节闭环元规则；整体由主Agent 把控"何时进下一环节"。

## 5. 实测示例（去本机路径，改用占位）

> 背景：把某"源项目"能力移植到"目标平台"网页版（以 `<示例项目>` 代指真实工程）。本示例选隔离沙箱作受控验证环境（v5 起 `working_dir` 默认用真实仓库，沙箱仅作硬约束/受控回退），`<示例项目>` 目录**零接触**（仅只读列举一次）。

### 示例一 · 讨论协同（范式A 串行交替审核）
**第1轮（主Agent → v1）**：prompt 要求提 3 条技术路线（A. API 代理桥接 / B. 纯提示词工程 / C. 本地中间层服务），"只分析不写文件"。mimo 返回 3 路线 + 对比表。
**第2轮（探测 continue_session）**：带 `continue_session=true` 追问比选 → 若 mimo 回"没有上一轮上下文"，**记录该环境无状态**，后续全靠回灌。
**第3轮（mimo → 审核报告 + v2）**：回灌"背景回顾（3 路线评估）+ 决策（B 为主、C 为补充）"，要求"先给 v1 的【审核报告】，再产出【v2 架构草图】"。mimo 返回：审核报告（含 B 受上下文长度限制等风险）+ 完整模块架构（目录+职责+下沉能力+路由伪代码）。
**第4轮（主Agent → 审核报告 + v3）**：主Agent 审阅 v2 架构，出具审核报告（指出"本地中间层状态管理缺持久化方案"），产出 v3（补充持久化与回退策略）。回灌 mimo。
**第5轮（mimo → 审核报告 + v4）**：mimo 审核 v3，确认无新增异议，微调后给 v4 一致草图。
**结果**：多轮交替审核在"主Agent 回灌"下连贯可行，最终形成唯一一致架构方案。

### 示例二 · 调研搜索（范式B 并行交叉审核）
> 设计形态，首次使用按此实测一遍以确认本环境行为。
**第1步（并行）**：主Agent 执行 `gh search code "xxx"` 取仓库内相关实现；同时 mimo 并行联网搜索同类方案（prompt："只分析不写文件，产出可复核的调研笔记"）。
**第2步（交叉互审）**：主Agent 把 `gh` 结果给 mimo 审（"请审核以下搜索结论，指出遗漏/风险"）；mimo 把调研笔记回灌主Agent 审。
**第3步（合成）**：主Agent 汇总双方审核报告，合成调研结论与实现建议 → 闭环。
**边界**：`gh` 搜索与任何真实 git 动作为主Agent 独占；mimo 只产出可复核文本。
