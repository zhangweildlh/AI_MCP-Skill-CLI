# SilvereWolf/idea-friction-feasibility-auditor 模块方法论缓存

**模块用途**：Phase 2 问题审查增强——提供结构化的可行性审计与 Steelman 双方分析
**激活条件**：问题复杂度 ≥ 中 或 信息不明确
**接口契约**：
- 输入：`{ "用户问题描述": str, "已有信息": [str], "用户初步判断": str|null }`
- 输出：`{ "audit": {"facts": [str], "assumptions": [{"内容":str,"类型":"load-bearing|decorative|hidden"}], "unknowns": [{"项":str,"优先级":"必须有|最好有|锦上添花"}]}, "steelman_pro": [str], "steelman_con": [str], "verdict": "可行/有条件可行/不可行/需更多信息", "value_flaw": str|null }`

---

## 核心方法论

### 1. Audit（审计——分离事实/假设/未知）

**目的**：将用户输入的混杂信息拆解为三类可处理的元素，避免"假设当事实"或"未知当已知"的思维陷阱。

**执行步骤**：

1. **提取 Facts（事实）**
   - 标准：可独立验证、无争议、具体的观察或数据
   - 示例：「日志显示 Error 500 发生 47 次」「用户在 Chrome 120 上复现」「API 响应时间 p99=2.3s」
   - 非事实：「系统很慢」「代码有问题」「应该是内存泄漏」

2. **识别 Assumptions（假设）**
   - 标准：用户或你隐含前提、未经验证但支撑推理链的陈述
   - 每个假设必须标注类型：
     - `load-bearing`（承重假设）：若该假设不成立，整个推理链崩塌
     - `decorative`（装饰性假设）：不影响核心结论，仅作背景
     - `hidden`（隐性假设）：用户未说出口但推理依赖的前提
   - 示例：「假设数据库连接池配置未变更 (load-bearing)」「假设用户网络正常 (decorative)」「假设没有并发写入冲突 (hidden)」

3. **列出 Unknowns（未知）**
   - 标准：分析必须但当前缺失的信息
   - 按优先级标注：
     - `必须有`：缺它无法继续分析
     - `最好有`：有它显著提升置信度
     - `锦上添花`：有助于完善但非关键
   - 示例：「最近一次部署变更记录 (必须有)」「数据库慢查询日志 (最好有)」「用户完整操作路径 (锦上添花)」

**输出格式**：
```markdown
## Audit 结果

### Facts（事实）
- [事实1]
- [事实2]
...

### Assumptions（假设）
- [内容] —— 类型：load-bearing|decorative|hidden
- [内容] —— 类型：load-bearing|decorative|hidden
...

### Unknowns（未知）
- [未知项] —— 优先级：必须有/最好有/锦上添花
- [未知项] —— 优先级：必须有/最好有/锦上添花
...
```

### 2. Steelman 双方分析（钢人双方）

**目的**：避免确认偏误，强迫自己从最强支持方和最强反对方两个视角审视问题，确保审查的深度和公正性。

**执行步骤**：

1. **Steelman Pro（最强支持案）—— 论证"问题成立/方案可行"**
   - 收集所有支持用户判断/提案的证据、逻辑、先例
   - 强迫自己把支持案写到最强，哪怕你内心倾向反对
   - 包含：数据支撑、类似场景成功先例、理论依据、专家共识

2. **Steelman Con（最强反对案）—— 论证"问题不成立/方案不可行"**
   - 收集所有反对用户判断/提案的证据、反例、风险点
   - 强迫自己把反对案写到最强，哪怕你内心倾向支持
   - 包含：已知失败案例、理论冲突、资源/时间约束、隐性依赖风险、Value Flaw（价值缺陷：解决了也没用、解决错问题、副作用大于收益）

**Value Flaw（价值缺陷）识别**：
- 即使技术可行，是否解决了错问题？
- 解决后收益是否大于成本？
- 是否存在更简单的替代方案达到同等效果？
- 是否会引入更大的系统性风险？

**输出格式**：
```markdown
## Steelman 双方分析

### Steelman Pro（最强支持案）
- [支持理由1]
- [支持理由2]
- [支持理由3]
...

### Steelman Con（最强反对案）
- [反对理由1]
- [反对理由2]
- [反对理由3]
...

### Value Flaw（价值缺陷）
[若发现价值缺陷，明确描述；否则标注"未发现明显价值缺陷"]
```

### 3. 融入原有三层审查

将 Audit 和 Steelman 结果映射到 Phase 2 原有三层结构：

| 原有审查层 | 融入增强内容 |
|------------|--------------|
| 问题成立性 | 参考 Steelman Con 的 Value Flaw、反对理由强度；若 Steelman Con 显著强于 Pro，质疑问题成立性 |
| 信息充足度 | 直接使用 Unknowns 列表，按优先级告知用户缺什么 |
| 隐藏问题 | 重点关注 load-bearing 假设——若承重假设不成立会导致什么后果；Steelman Con 中的新风险点 |

**融合输出格式**：
```markdown
## Phase 2：问题审查

### 问题成立性
[你的判断 + 理由，引用 Steelman Con 的关键点]

### 信息充足度
[已有信息概述 / 缺失信息 / 对分析的影响，引用 Unknowns 列表]

### 潜在隐藏问题
[发现的其他问题 / load-bearing 假设风险 / Steelman Con 新风险点]

### SilvereWolf 增强输出
- Facts: [列表]
- Assumptions: [列表，每项标注类型]
- Unknowns: [列表，每项标注优先级]
- Steelman Pro: [列表]
- Steelman Con: [列表]
- Value Flaw: [描述或"无"]
- Verdict: [可行/有条件可行/不可行/需更多信息]
```

---

### 4. Verdict（裁决）与行动建议

基于融合审查给出明确裁决：

| 裁决 | 含义 | 后续行动 |
|------|------|----------|
| 可行 | 问题成立、信息充足、无重大隐患 | 直接进入 Phase 3 |
| 有条件可行 | 问题基本成立，但需验证关键假设 | 列出需验证的 load-bearing 假设，要求用户补充或进入 Phase 3 时标注为假设 |
| 不可行 | 问题不成立、或 Value Flaw 致命、或 Steelman Con 压倒性强 | 直接反馈用户，建议重新定义问题或放弃 |
| 需更多信息 | Unknowns 中"必须有"项未满足 | **暂停后续流程**，明确列出必须补齐的信息，等用户回复 |

## 降级方案（模块不可用时）

退化至原有三层审查（问题成立性/信息充足度/隐藏问题）：
- 手动拆解用户输入中的事实、假设、未知
- 手动从正反两面思考，写出简化版 Steelman
- 输出中标注：`[SilvereWolf Consult 模块暂不可用，已切换至基础审查模式]`
