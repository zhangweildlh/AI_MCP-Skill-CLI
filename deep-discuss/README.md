# Deep Discuss — 结构化深度讨论（v2.0 模块化版）

## 一、用户指南（大白话篇）

### 什么是 Deep Discuss？

Deep Discuss 是一个引导你与 AI 进行**深度、结构化问题讨论**的技能。当你有一个问题、困惑或需要深入思考的事情时，它会带你走完一个 7 阶段的思考流程，确保不急于下结论，先把问题想透。

它像一位经验丰富的思考伙伴，会问：“这个问题真的存在吗？”“信息够吗？”“有没有我们没注意到的其他问题？”——帮你避免答非所问或遗漏关键点。

### 我什么时候应该用它？

- 你描述了一个问题但不确定是否真的是问题
- 你感觉信息不足，想知道还需要什么才能继续分析
- 你想探索多种可能性，而不仅是最显眼的那个
- 你需要一个方案，但希望它经得起推敲，考虑周全
- 你想检查自己的想法是否有盲点或假设
- 你直接说出了这些触发短语之一：「讨论一下」「帮我分析」「我遇到一个问题」「你觉得怎么样」「帮我想想」「我在纠结」

### 它会怎么工作？

整个讨论分为 7 个阶段，每个阶段都有明确的目的和输出。你会在每次回复开头看到当前阶段的标注，比如 “Phase 2 → 问题审查”，这样你知道我们在讨论什么。

#### 7 阶段流程：
1. **接收信息**：只收集你提供的一切，不急于分析
2. **问题审查**：审视问题本身是否成立、信息是否充足、是否有隐藏问题
3. **深度分析**：追根溯源，考虑多种可能性
4. **方案设计**：给出 2-3 个可选方案，说明 trade-off
5. **方案自检**：主动审查自己的方案有没有漏洞
6. **最终确认**：用户确认后做最后检查，索取具体行动承诺
7. **执行**（可选）：只有你说“开始”时才执行方案

### 特色功能：智能模块增强

从 v2.0 开始，Deep Discuss 支持懒加载的智能增强模块，在需要时自动激活：

- **5Why 模块（Phase 3）**：当需要深度分析时，使用丰田 5Whys 逐级追问根因
- **Premortem 模块（Phase 5-6）**：当方案复杂度高时，进行事前验尸，找出可能的失败模式
- **Consult 模块（Phase 2）**：当问题复杂或信息不明确时，进行事实/假设/未知的审计分析 + Steelman 双方辩论

这些模块是**按需激活**的，不用时不会加载；出问题时会自动降级到基础实现，不影响整个流程。

### 使用技巧

- **提供完整信息**：越详细的描述越好，包括背景、现象、你的猜测、截图等
- **承认不确定**：如果你不确定某件事，直接说出来，比猜测更有帮助
- **耐心走流程**：哪怕问题看起来简单，也建议走完前 4 个阶段
- **欢迎反思**：如果 AI 的判断让你不爽，直接说出来，我们可以讨论分歧
- **关注阶段标注**：每次回复开头的 “Phase X” 帮你了解进度

### 常见问题

**Q：我想快速得到答案，可以跳过阶段吗？**  
A：可以，但不推荐。Phase 2 是质量门控，跳过可能导致答非所问。如果真的很急，至少完成 Phase 1-2。

**Q：AI 说需要更多信息，但我觉得已经够了？**  
A：请相信它的判断。它可能发现了你没注意到的隐藏假设或缺失的关键数据。

**Q：我可以中途改变方向吗？**  
A：可以！如果你提供了新信息，我们可能需要回到更早的阶段重新审查。

**Q：这些模块需要联网或额外配置吗？**  
A：不需要。所有模块方法论都已缓存到本地，离线也能用。版本通过锁定机制管理，确保稳定。

## 二、技术使用手册（Agent 专用篇）

### 如何调用？

Deep Discuss 是一个标准 WorkBuddy Skill。在对话中，当用户描述需要深度讨论的问题时，你应该主动激活它。

调用方式：在你的内部思考或工具链中，识别到需要结构化深度讨论的场景时，启动 Deep Discuss 流程。

**重要**：每次回复开头必须标注当前阶段，例如：
```
Phase 2 → 问题审查
```
或阶段转换时：
```
Phase 2 done → Phase 3：深度分析
```

### 模块接口契约

所有增强模块通过结构化 JSON 输入/输出与主干通信。主干只负责调度和结果融合，不感知模块内部实现。

#### 1. SilvereWolf Consult 模块（Phase 2 问题审查增强）

**激活条件**：问题复杂度 ≥ 中 或 信息不明确  
**输入**：
```json
{
  "用户问题描述": "用户原始问题的文字描述",
  "已有信息": ["信息1", "信息2", "..."],
  "用户初步判断": "用户自己的初步看法（可为 null）"
}
```
**输出**：
```json
{
  "audit": {
    "facts": ["事实1", "事实2", "..."],
    "assumptions": [
      {"内容": "假设内容", "类型": "load-bearing|decorative|hidden"},
      {"内容": "假设内容", "类型": "load-bearing|decorative|hidden"}
    ],
    "unknowns": [
      {"项": "未知项1", "优先级": "必须有|最好有|锦上添花"},
      {"项": "未知项2", "优先级": "必须有|最好有|锦上添花"}
    ]
  },
  "steelman_pro": ["支持理由1", "支持理由2", "..."],
  "steelman_con": ["反对理由1", "反对理由2", "..."],
  "verdict": "可行/有条件可行/不可行/需更多信息",
  "value_flaw": "价值缺陷描述或 null",
  "待验证假设": ["假设1", "假设2", "..."]
}
```

### 版本锁定与依赖管理

所有外部依赖通过 commit hash 锁定，具体参见技能根目录的 `version-lock.md` 文件。

**锁定的模块**：
- jasminK11/claude-5-why-skill（用于 Phase 3 深度分析）
- kimasplund/premortem-skill（用于 Phase 5 方案自检和 Phase 6 最终确认）
- SilvereWolf/idea-friction-feasibility-auditor（用于 Phase 2 问题审查）

**更新流程**：
1. 每季度检查上游仓库是否有新版本（仅读取 CHANGELOG 或标签，不自动拉取）
2. 仅当确认更新不破坏接口契约时，才考虑更新 `version-lock.md` 中的版本号
3. 更新前必须在隔离环境中验证新版本与主干的兼容性
4. 更新后运行回归测试（使用典型问题场景走查完整流程）

### 降级机制

任何依赖模块不可用时（虽然本地缓存使这种情况罕见，但为了健全性）：
- **Phase 2**：退化至原有三层审查（问题成立性/信息充足度/隐藏问题）
- **Phase 3**：退化至多维度脑暴雨式分析（考虑技术/流程/风险/成本等维度）
- **Phase 5**：退化至原有检查清单（5项）
- **Phase 6**：退化至原有四项检查（完整性/风险预案/验证方式/补充建议）

在阶段输出中明确标注：`[模块名称] 暂不可用，已切换至基础模式`

### 故障排查

| 问题 | 检查点 | 解决方案 |
|------|--------|----------|
| 提示模块版本不匹配 | 检查缓存文件首行的 `<!-- 版本锁定: commit:... -->` 是否与 `version-lock.md` 一致 | 重新缓存对应模块或更新 version-lock.md |
| 流程卡在某阶段 | 检查是否有未解决的“必须有”未知项需要用户补充 | 按 Unknowns 优先级引导用户提供信息 |
| 输出格式混乱 | 检查是否正确使用了模板文件 | 使用 `assets/templates/` 下的对应模板 |
| 怀疑降级了却未提示 | 检查相关缓存文件是否存在并完整 | 验证 `references/enhancements/` 下的三个模块文件 |

### 上游演进自主检查

作为维护者，你应该定期检查上游模块是否有更新：

1. **查看最新 tag**：
   ```bash
   git ls-remote https://github.com/jasminK11/claude-5-why-skill.git refs/tags/*
   git ls-remote https://github.com/kimasplund/premortem-skill.git refs/tags/*
   git ls-remote https://github.com/SilvereWolf/idea-friction-feasibility-auditor.git refs/tags/*
   ```

2. **阅读 CHANGELOG**：重点关注是否有破坏性变更（特别是接口修改）

3. **检查是否需要更新**：
   - 仅文档/注释更新：可选更新
   - 非破坏性功能增强：推荐更新（需接口兼容性测试）
   - 接口修改/核心行为变更：谨慎更新（需完整回归测试+适配层）
   - 安全修复：强制更新

4. **更新前的隔离验证**：
   - 在临时分支或worktree中更新 version-lock.md
   - 用典型问题运行完整 Deep Discuss 流程
   - 验证输出格式和行为不变

## 三、维护者须知

### 本技能的设计哲学

- **稳定性第一**：主干 SKILL.md 只定义流程框架和接口，不绑定具体实现
- **低维护成本**：通过版本锁定和懒加载，减少因上游更新导致的破坏
- **故障隔离**：单个模块不可用不会影响整个流程
- **清晰的责任界限**：主干负责流程调度，模块负责具体算法

### 对未来贡献者的建议

1. **不要修改主干流程**：除非绝对必要，否则不要改变 7 阶段的基本结构
2. **增强而非替代**：新模块应作为现有阶段的增强，而非替换
3. **保持接口稳定**：一旦约定了输入/输出格式，不要轻易改变
4. **文档即契约**：所有接口变更必须更新本 README 和对应模块的方法论缓存文件
5. **优先离线**：所有增强都应有本地缓存方案，确保网络不可用时仍能工作

> Deep Discuss v2.0 通过模块化架构，在保持经典 7 阶段流程稳定性的同时，引入了可按需激活的智能增强能力。它不试图成为万能的解决方案引擎，而是专注于做好一件事：引导思考过程，让每次讨论都有深度、有结构、有出路。
