## 1. 问题 1 核查（真实逻辑缺口，建议修）

### 1.1 证据链

**(a) 模板侧——字段确实缺失**
- `assets/_流水线状态.md` 全 168 行，结构为 §1–§12。其中 §9「双引擎搜索能力状态」（L116–L127）仅含：
  - `AnySearch 可用状态：[可用/不可用]`
  - `Firecrawl 可用状态：[可用/不可用]`
  - `组合判定`（双可用 / 单可用 / 双不可用）
  - **无「Firecrawl 访问形态（直连 / 中继经 Dynamic-mcp / 不可用）」字段。**
- 全文唯一出现「工具能力映射表」在 §5 使用说明 L166：`...所有占位符已被替换为实际值（工具能力映射表等）`——仅作为"待替换占位符"被提及，**模板正文无任何 `[工具能力映射表]` 占位符、也无 `## 工具能力映射表` 小节**，§2「全局参数」下也无该插槽。即模板承诺了占位符却未定义落点。

**(b) 引用侧——16 个文件依赖该字段**
grep `工具能力映射表` 命中 16 个文件：`_router/` 全部 step-01~10 + _contract + bootstrap、SKILL.md、references/02 + 15、assets/_流水线状态.md。关键硬约束：
- `bootstrap.md` L54：「在映射表中额外记录 … Firecrawl 的 … **访问形态**（直连 / 中继经 Dynamic-mcp / 不可用）」
- `bootstrap.md` L56：「Firecrawl 的访问形态 … 写入『工具能力映射表』」
- `bootstrap.md` L63：「将探测结果整理为『工具能力映射表』，作为状态文件的**一个独立字段**」
- `bootstrap.md` L66（[产出]）：状态文件「全局参数含『工具能力映射表』」
- `bootstrap.md` L73（[验证]）：「确认『工具能力映射表』字段已写入」
- `step-05.md` L77：「Firecrawl 调用形态**依状态文件『工具能力映射表』**记录的形态」
- `15-resume-protocol.md` L13/L57/L71/L78/L111/L125：续跑「**依状态文件『工具能力映射表』的形**态」「以映射表为准」「形态按映射表生效」
- `SKILL.md` L40/L75/L86：明确「创建状态文件并写入『工具能力映射表』」「Firecrawl 访问形态由 Gate-0 探测写入『工具能力映射表』」

**(c) 矛盾点**
引用侧把「工具能力映射表」（含 Firecrawl 访问形态）定义为状态文件的**正式、持久化、续跑权威**字段；但唯一的权威 schema（模板 `assets/_流水线状态.md`）未定义该插槽，§9 也不记录形态。结果：传输无关化后，"形态"这一关键信息**没有正式持久化位置**，续跑会话依赖一个模板未定义的 ad-hoc 字段 → 存在形态丢失 / 需重探风险，与「续跑与首会话形态一致」（15-resume-protocol L78、SKILL L86）要求有张力。

### 1.2 判定
**真实逻辑缺口，成立。** 影响为契约不一致而非运行崩溃，首会话不受影响，仅续跑一致性受损——与问题描述的中高严重度一致。

### 1.3 建议修复（与问题描述一致，可直接落地）
1. 在 `assets/_流水线状态.md` §9 增加一行：
   ```
   - Firecrawl 访问形态：[直连 / 中继经 Dynamic-mcp / 不可用]
   ```
2. 新增 §13「工具能力映射表」（或明确写入 §2 全局参数下），并提供占位符 `[工具能力映射表]`，使 bootstrap L63/L66/L73 与 §5 L166 的"占位符"有正式落点。
